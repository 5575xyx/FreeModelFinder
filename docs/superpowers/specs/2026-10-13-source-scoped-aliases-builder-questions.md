## Questions that would change the plan

### 1. (High) Concurrent-edit / stale-read conflict on the global modelAliases map

The new flow adds a GET /api/model-aliases read into saveCustomProvider, then a
write of the merged map. This is a read-modify-write on a globally shared map.
If two dashboard tabs are open, or if the user switches between the old
"Models" tab (before the design is fully shipped) and the new Custom tab, a
last-write-wins PUT from the old tab could silently overwrite the new
tab's source-scoped aliases.

**What I need to know:** Is last-write-wins acceptable (simplest), or do we
need re-read-before-write / ETag / If-Match conflict detection? If acceptable,
the answer is "just use last-write-wins, no extra mechanism needed". If not,
we need to add a re-fetch step and a conflict-resolution UI (show a banner
"Aliases changed elsewhere, reload?" before overwriting).

**Why it matters:** This is the single biggest UX risk in the feature. A wrong
guess here means either (a) silent data loss on concurrent edit, or (b)
over-engineering a conflict-resolution layer that the design explicitly
excluded (最小侵入版).

### 2. (High) Re-creation of a deleted source id — does the alias map hydrate?

The rules say "delete source strips all source-id/* aliases". Now suppose a
user deletes source `nova` (all `nova/*` aliases stripped), then _re-creates_
a source also called `nova`. The new source's editor loads aliases for `nova`
from the global map. But all `nova/*` entries were just stripped. Should the
new source's editor:

(a) start empty (user must re-create all aliases), or
(b) re-fetch from the server after the sources POST and show any surviving
`nova/*` entries?

The design says "来源 id 重命名 不支持" so the _intent_ is (a) — deleted aliases
are gone and re-creation starts fresh. But the alias map is a _global_ map that
other entry points (future tools, hand-edited config.json) can also write to.
If someone hand-edits config.json to re-add `nova/glm` between delete and
recreate, the UI's source-of-truth (the global map read at save-time) would
find the hand-edited entry and preserve it.

**What I need to know:** Is the alias map's state owned exclusively by the UI
saveCustomProvider flow, or can it be mutated externally (CLI, hand-edit,
removal-cleanup) such that the UI must re-read it to stay correct?

**Why it matters:** If external mutations are possible (and they are —
removal-cleanup.ts already prunes aliases for upstream providers), then the UI
should re-read the map before each save to pick up external changes, which
changes the read/write flow and the test expectations.

## Non-blocking observations

- defaultModel pointing at a deleted source's model is not covered by the
  alias-rewrite rules. Out of scope per the design, but worth noting as a
  known-gap follow-up.
- The GET /api/model-aliases dependency means the Custom tab save now has a
  network call that previously belonged to the Models tab. If that GET fails,
  the save aborts with a generic "save failed" toast. Acceptable, but the
  toast message could be more specific.
